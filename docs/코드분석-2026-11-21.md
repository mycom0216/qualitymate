## 1. 이번 오류와 수정 결과

`제품 가격은 얼마인가요?`라는 질문에 `흠집 제품은 출하를 보류한다`는 답이 나왔다. 기존 검색은 질문의 단어와 문서 본문이 하나라도 겹치면 검색 결과로 채택했다. `제품`은 모든 문서에 흔하게 있으므로 가격 정보가 없어도 관련 없는 절이 검색됐다. 이후 모델 출력 스키마의 `minItems=1` 때문에 모델은 문장을 반드시 골라야 했다.

수정한 처리는 지원하지 않는 질문을 먼저 거르고, 지원하는 의도에 맞는 원문 문장만 후보로 만든다. 따라서 가격 질문은 LLM을 호출하지 않고 `no-evidence`를 반환한다. 가격 숫자, 불량 원인, 실제 판정 등을 모델이 만들지 않는다.

실제 모델 테스트 56개와 모의 모델 오류 테스트 11개가 통과했다. 이는 지정한 입력에 대한 결과다. 모든 한국어 질문에 대한 정확도를 뜻하지 않는다. 실제 모델을 호출한 질문 20개의 최종 반복 측정에서는 12개가 `llm`, 8개가 `source-only`였다. `source-only`는 모델의 선택이 비어 서버가 원문을 표시한 경로이므로 AI 답변 성공으로 계산하지 않는다.

## 2. 전체 요청 흐름

```text
브라우저 index.html / app.js
  → HTTP API Program.cs
    → 제품 사실: InspectionStore.cs → SQLite
    → 질문 의도: KnowledgeBase.cs → standards.json
    → 지원하지 않음: no-evidence, 모델 호출 없음
    → 제품 기록 질문: record, 모델 호출 없음
    → 지원하는 절차 질문: 관련 원문 후보 → Ollama
        → 올바른 번호: llm, 번호에 해당하는 원문만 출력
        → 빈 선택: source-only, 검색된 원문임을 명시
        → 통신/JSON/번호 오류: retrieval-only, 출처를 펼쳐 확인
```

AI는 제품 합격 여부를 판정하거나 재검사 결과를 저장하지 않는다. 판정 변경은 사용자가 재검사 폼을 작성한 뒤 저장 API를 호출할 때만 일어난다.

## 3. Program.cs

### 초기화와 의존성 등록

`--diagnose`가 있으면 웹 서버 대신 `RuntimeDiagnostics.RunAsync`를 실행한다. 일반 실행에서는 ASP.NET Core를 만들고 `InspectionStore`, `KnowledgeBase`를 Singleton으로 등록한다. 각 저장 작업은 별도의 SQLite 연결과 트랜잭션을 열기 때문에 Singleton이 DB 연결 자체를 공유하는 구조는 아니다.

`AddHttpClient("ollama")`는 Ollama 주소와 90초 제한을 설정한다. 비동기 호출을 사용하므로 기다리는 동안 스레드를 계속 점유하는 방식은 아니다. `UseDefaultFiles`와 `UseStaticFiles`는 `/`에 index.html을 보내고 JS/CSS를 제공한다.

### API별 역할

| API | 역할 | 주요 실패 응답 |
| --- | --- | --- |
| GET /api/inspections | 최초 검사와 재검사 이력 조회 | DB 접근 실패는 서버 오류 |
| GET /api/documents | 표준서 4개 절 조회 | 표준서 로딩은 시작 때 수행 |
| GET /api/status | Ollama 태그에서 모델 설치 확인 | 연결/JSON/필드 오류면 aiReady=false |
| POST /api/chat | 사실 조회, 질문 분류, 근거 선택 | 빈 질문 400, 없는 제품 404 |
| POST /api/import/visionqc | CSV 전체 파싱 후 가져오기 | 형식 400, 기존 내용 충돌 409 |
| POST /api/inspections/{id}/reinspections | 사용자 판정과 메모 추가 | 입력 400, 제품 없음 404, 버전 충돌 409 |

`aiReady=true`는 태그 목록에 설정 모델이 있다는 뜻이다. 실제 생성 성공이나 GPU 정상 여부까지 보장하지 않는다. 생성 검증은 실제 `/api/chat` 호출로 따로 수행했다.

### /api/chat 상세

1. 질문 공백과 2,000자 초과를 거부한다.
2. 선택한 제품을 조회한다. 없는 제품에 대한 사실을 지어내지 않는다.
3. `kb.Plan(question, product)`으로 관련 문장과 기록 답변을 얻는다.
4. `RecordAnswer`가 있으면 DB에서 계산한 답을 바로 보낸다.
5. 관련 절이 없으면 `no-evidence`로 끝낸다.
6. 문장에 0부터 번호를 붙여 Ollama에 보낸다.
7. JSON의 `evidenceIds` 배열을 파싱하고 원시 배열 길이, 정수 형식, 0 이상, 후보 개수 미만인지 확인한다.
8. 유효한 번호만 서버의 원문에 연결한다. 모델의 자유 텍스트를 사용자 답변으로 쓰지 않는다.

`rawIds`의 길이를 중복 제거 전에 검사한다. `[0,0,0,0,0]`을 중복 제거하면 1개지만, 원래 4개 제한을 어긴 출력이므로 거부해야 한다. 잘못된 정수 번호, JSON 누락, 문자열 번호 등은 `retrieval-only`로 전환한다.

빈 선택은 통신 장애가 아니다. 이를 `source-only`로 분리해 화면에 `표준서 원문 · AI 선택 없음`이라고 보여 준다. `model=null`로 돌려줘 실제 LLM 답변과 구별한다. 연결/형식 오류는 서버 로그에 예외 종류만 남긴다.

### 데이터 모델

`Inspection.Revision`은 재검사 개수다. 별도 버전 컬럼은 없다. `CurrentResult`는 마지막 재검사 결과이며 없으면 최초 결과다. 따라서 최초 기록을 수정하지 않아도 최신 상태를 계산할 수 있다. 최초 FAIL, 재검사 PASS이면 최초 불합격과 현재 합격이 공존한다.

## 4. KnowledgeBase.cs

기존 Program.cs 내부 검색 클래스를 파일로 분리했다. `Section`은 문서 절, `Evidence`는 한 문장, `QueryPlan`은 반환할 출처·문장·기록 답변·안내문을 담는다.

### 문서 로딩

생성자에서 JSON을 읽는다. 현재 문서는 시연용 4개 절이다. PDF 업로드, 임베딩, 벡터 DB는 구현하지 않았다. JSON의 Keywords는 기존 자료와 호환을 위해 남아 있지만 이번 분류는 Keywords 점수를 사용하지 않는다.

### Plan 함수

- 질문을 소문자로 바꾸고 연속 공백을 정리한다.
- 가격, 비용, 예산, 반품, 폐기 등 SOP에 없는 요청을 거절한다.
- 현재/최초 판정, 재검사 횟수, LOT는 DB에서 답한다.
- 재검사, 기록, 이력, 출하, 조건, 흠집, 이물, 보관, 보증 등 지원하는 의도를 구별한다.
- 일반적인 불량 원인 질문에는 해당 제품의 관찰을 참고한다. 흠집 제품은 SOP-01, 이물 제품은 SOP-02를 쓴다.
- 합격 제품에 불합격 이유를 물으면 불합격 기록이 없음을 알린다.
- ERROR 제품은 검사 오류임을 알리고, 유형 미확인 NG에 흠집이나 이물을 임의로 붙이지 않는다.
- 복합 질문은 서로 필요한 문장을 모아 모델에 보낸다.

### Pick 함수

절 ID와 그 절 안의 특정 구절을 사용해 실제 원문 문장을 선택한다. 답변 문자열을 별도로 새로 작성하는 대신 원문을 그대로 사용한다. 예를 들어 재검사 기록 질문이면 `메모를 필수`가 들어 있는 SOP-03 문장을 고른다.

이 구조는 4개 시연 SOP에 맞춘 규칙 기반 검색이다. BM25나 의미 검색이라고 설명하면 안 된다. 문서가 늘거나 SOP 문장을 바꾸면 규칙도 검토해야 한다. `Single`은 기대한 문장이 없거나 중복이면 예외를 내므로, 문서 개정 후에는 질문 회귀 테스트가 필요하다. 알 수 없는 동의어나 복합 주제는 여전히 놓칠 수 있다.

지원하지 않는 단어 목록은 범위 밖 질문을 모두 이해하는 장치가 아니다. 예를 들어 부정문이나 문맥 반전까지 한국어 의미를 일반적으로 판별하지 못한다. 지원 범위를 넓히려면 새 문항을 별도로 만들고 이 분류와 검색 방식을 함께 평가해야 한다.

## 5. InspectionStore.cs

### 생성자와 테이블

`DataDirectory` 설정 또는 프로젝트 data 폴더 아래에 SQLite 파일을 만든다. 외래키를 켜고 WAL 모드를 사용한다. Inspections에 최초 검사, Reinspections에 추가 검사 기록을 분리한다. 판정 CHECK 제약과 RequestId UNIQUE 제약이 있다.

DB가 비어 있으면 기존 inspections.json을 이관하거나 시연 제품 3개를 넣는다. 기존 JSON은 삭제하지 않는다. 이 코드는 초기 생성 처리이며, 버전별 스키마 마이그레이션 체계를 가진 것은 아니다.

### All / Read

하나의 읽기 트랜잭션 안에서 최초 검사 목록과 재검사 목록을 읽어 연결한다. 재검사는 Sequence 순서로 정렬해 마지막 결과를 계산한다. 한 요청의 목록과 이력은 같은 DB 스냅샷을 사용한다.

모든 제품과 재검사를 메모리에 읽기 때문에 데이터가 커지면 비효율적이다. 현재는 소규모 로컬 시연에 적합하다. 운영 범위로 넓힐 때 제품별 조회와 페이지네이션을 추가해야 한다.

### Append

트랜잭션을 연 뒤 제품과 요청 ID를 확인한다. 같은 요청 ID와 같은 내용이면 이전 성공 결과를 돌려준다. 같은 ID에 다른 내용을 보내면 409다. 이 중복 검사 후 `ExpectedRevision`을 비교하므로, 성공 응답을 못 받은 클라이언트가 같은 요청을 재전송해도 오래된 버전 오류 대신 성공 상태를 받을 수 있다.

새 요청은 서버의 현재 Revision과 클라이언트 ExpectedRevision이 같을 때만 저장한다. SQLite 쓰기 트랜잭션 안에서 비교와 삽입을 하므로 동시에 같은 버전으로 저장하면 하나만 성공하고 나머지는 409가 된다. 검사자와 메모는 Trim한 값을 저장한다.

SQL은 `$id`, `$note` 같은 매개변수를 사용한다. 사용자 메모를 SQL 문자열에 이어 붙이지 않는다. 이번 테스트에서는 중복 요청, 다른 내용 재사용, 오래된 버전, 동시 저장을 직접 확인했다.

### Import

파일의 행을 하나의 트랜잭션에 넣는다. 같은 제품 키에 원본 내용이 같으면 중복 제외, 다르면 409다. 충돌 전에 새 행을 삽입했더라도 Commit하지 않고 반환하면 트랜잭션 폐기 시 롤백된다. 파일 일부만 남지 않도록 만든 구조다.

## 6. VisionCsv.cs

`TextFieldParser`를 사용하므로 CSV의 따옴표와 쉼표를 처리할 수 있다. 헤더 8개를 정확히 비교한 뒤 ID·작업 ID·시각·점수·처리 시간·판정을 검증한다. 파일 내 중복 검사 ID와 1,000행 초과를 거절한다.

- `OK → PASS`, `NG → FAIL`, `ERROR → ERROR`로 변환한다.
- `Id + JobId → VQC-{job}-{id}`로 외부 검사 키를 만든다.
- NG 점수로 불량 유형을 추측하지 않는다.
- 오류 행의 ErrorMessage는 관찰로 보존한다.

수정 1: `csv.Length`는 글자 수이므로 1MB 제한과 다르다. 한글 333,334자는 UTF-8에서 1,000,002바이트다. `Encoding.UTF8.GetByteCount`로 실제 바이트 수를 검사하도록 고쳤다.

수정 2: UTF-8 BOM이 첫 헤더에 붙으면 정상 CSV를 거절하므로 시작 BOM을 제거한다.

수정 3: 시간대 없는 날짜를 서버 로컬 시각으로 해석하면 다른 PC에서 시각이 달라진다. ISO 8601 날짜와 T 시각 및 Z 또는 ±HH:mm을 요구한 뒤 TryParse로 실제 날짜 유효성을 검사한다. 원본 exporter의 7자리 소수 초와 Z 형식은 지원한다.

## 7. wwwroot/app.js

### api / post

fetch로 API를 부르고 JSON을 읽는다. HTTP 400/404/409의 error 문구를 화면 안내에 보여 준다. post는 Content-Type과 JSON 직렬화를 일관되게 만든다. 서버가 JSON 대신 HTML 오류 페이지를 내는 경우 현재는 JSON 파싱 오류가 표시될 수 있다.

### escapeHtml

사용자 메모, 관찰, 모델 답변에 포함된 `& < > " '`를 HTML 엔티티로 바꾼다. innerHTML로 카드와 이력을 만들 때 삽입된 문자열이 실행되지 않게 하는 데 중요하다. 답변은 escape한 다음 SOP 인용 패턴만 span으로 바꾼다.

### renderList / renderDetail / load

검색은 제품 ID 부분 일치다. 선택한 제품의 최초/현재 판정, 관찰, 시각, 재검사 이력을 보여 준다. load는 API에서 다시 읽고 기존 선택 제품을 유지한다. 화면의 불합격 지표는 현재 불합격 개수가 아니라 InitialResult=FAIL 개수이며 라벨도 `최초 불합격`이다.

### 재검사 submit

result, operator, note, expectedRevision을 만든다. 요청 내용의 signature가 같으면 이전 requestId를 재사용한다. 사용자가 저장 성공을 못 받은 뒤 재시도해도 같은 요청임을 서버가 알 수 있다. 성공한 뒤 retryRequest를 비우고 서버 데이터를 다시 읽는다.

busy와 버튼 disabled는 같은 탭에서의 중복 조작을 줄이는 장치다. 다른 브라우저까지 막는 장치는 아니므로 서버 트랜잭션과 버전 검사가 따로 필요하다.

### chat submit

선택한 제품과 질문을 보내고 기다림 표시를 띄운다. 응답의 mode별로 화면 라벨을 다르게 붙인다.

| mode | 사용자에게 보이는 의미 |
| --- | --- |
| llm | AI 근거 선택 + 모델명 |
| record | 검사 기록 기준 |
| source-only | 표준서 원문 · AI 선택 없음 |
| no-evidence | 근거 없음 |
| retrieval-only | AI 연결/형식 오류로 검색 원문 확인 필요 |

notice가 있으면 사실과 절차를 혼동하지 않도록 추가 설명을 보여 준다. 출처 절을 펼치면 표준서 원문과 버전을 확인할 수 있다.

### CSV import submit

File API로 로컬 파일을 읽고 CSV 문자열을 서버에 전송한다. 입력 파일 크기 검사와 서버의 UTF-8 크기 검사는 별도로 있다. 성공하면 추가/중복 수를 보여 주고 목록을 다시 읽는다. 실제 카메라 장치에 연결하는 코드는 아니다.

## 8. index.html, CSS, polish.js

index.html은 제품 목록·검사 상세·질문·표준서·CSV 폼을 만든다. app.js는 각 ID를 사용하므로 HTML ID를 바꿀 때 JS도 맞춰야 한다.

style.css → code-theme.css → polish.css → rose.css 순서로 로딩된다. 뒤에서 같은 선택자를 덮어써 최종 핑크 테마가 된다. CSS 파일이 여러 겹이라 유지보수 때 최종 규칙의 출처를 찾기 어려울 수 있다.

polish.js는 포인터 위치에 따른 장식 효과다. requestAnimationFrame으로 프레임당 갱신하고, 터치 입력이나 reduced-motion 설정에서는 효과를 줄인다. 업무 데이터와 저장에는 관여하지 않는다.

## 9. RuntimeDiagnostics.cs와 설정

필수 파일, Windows x64, 쓰기 권한, URLs·Ollama 설정, 모델 설치, 포트를 점검하고 environment-check.json을 만든다. 종료 코드 0은 준비, 1은 앱 환경 오류, 2는 AI 준비 필요다. 이미 QualityMate가 포트를 사용하면 중복 실행 대신 기존 페이지를 열도록 안내한다.

상태 JSON을 읽어 같은 서비스인지 확인하지만 인증된 서비스 식별은 아니다. 데이터 폴더가 별도 지정되면 기본 실행 폴더 쓰기 검사만으로 모든 저장 경로 권한이 보장되지 않는다.

QualityMate.csproj는 .NET 10 ASP.NET Core와 Microsoft.Data.Sqlite를 사용한다. submission/tmp/data가 빌드에 재귀 포함되지 않도록 제외한다. knowledge는 출력과 publish 결과에 복사한다. appsettings.json의 모델 이름은 Ollama에 설치된 이름과 같아야 한다. 모델 가중치는 EXE에 포함되지 않는다.

## 10. 테스트와 재현

`tools/test_rag_regression.py`는 별도 데이터의 테스트 서버에 실행한다. 기존 질문 20개, 추가 거절 12개, 동의어/복합 4개, 기록 4개, 근거 없는 인용 2개, 입력 검증 2개, 재검사 4개, CSV·상태 8개로 총 56개다.

평가 기준은 올바른 mode·출처·필수 문구와 실제 저장 결과다. 원문 표시인 source-only도 내용 검증에는 통과하지만 실제 AI 선택 성공 통계에는 넣지 않는다. 첫 수정에서는 원인 질문 2개가 불필요하게 거절돼 54/56이었고, 원문 직접 표시 경로를 분리한 뒤 56/56이다.

`tools/test_model_contract.py`는 로컬 모의 Ollama를 사용한다. 정상 번호, 빈 선택, message 누락, JSON 오류, 범위 초과, 음수, 문자열 번호, 5개 중복 번호, HTTP 503, 잘못된 tags 응답, 거절 질문의 모델 호출 생략을 총 11개 확인한다. 이 테스트는 실제 모델의 정확도나 속도를 측정하는 시험이 아니다.

로그와 JSON 결과는 `tmp/fix-2026-11-21`에 남긴다. 재검사/CSV 테스트는 DB 상태를 바꾸므로 `tools/test_fixed.py`이 매번 새 데이터 폴더로 서버를 만들게 했다. 평소 사용하는 DB에 테스트하지 않는다.

## 11. 수정 범위와 배포

수정 파일: Program.cs, VisionCsv.cs, wwwroot/app.js, wwwroot/index.html, tools/package_submission.py, README.md.
새 파일: KnowledgeBase.cs, 회귀/모델 계약 테스트, 격리 테스트 실행 도구, 이 분석 문서.
InspectionStore.cs와 표준서 원문은 변경하지 않았다.

원본 소스는 tmp/fix-backup-*에 보관한다. 배포 runtime도 교체 전 백업한다. 수정본의 source/runtime과 검사 결과를 담은 2026-11-21 ZIP을 별도로 만든다. 기존 2026-11-20 패키지는 이전 상태 비교용으로 남긴다.

운영용 인증·권한, 문서 업로드와 개정 관리, 대량 검색, 실제 제조 데이터 검증은 구현 범위에 없다. 이번 수정은 관찰한 오답과 입력 경계 오류를 고친 것이며 현장 도입 검증을 대신하지 않는다.

## 12. 배포 후 브라우저 캐시

실제 브라우저에서 서버의 record 응답이 이전 JS 라벨로 표시되는 문제를 확인했다. index.html은 Cache-Control: no-cache로 재검사하고 app.js 주소에 버전 쿼리를 붙였다. 이는 no-store와 달라 캐시 저장 자체를 금지하지는 않는다. API 서버와 UI 정적 자산이 서로 다른 버전으로 동작하는 문제를 줄이기 위한 수정이다.
